# Database — PostgreSQL + Drizzle

The production persistence. **Every repository interface now has a PostgreSQL
implementation**, and `src/data/backend.ts` is the one module that chooses
between them — from the server's environment, never from anything a browser can
set.

The HTTP layer that sits between them now exists: the browser signs in and
calls `/api/*`, and the routes run the application operations against whichever
persistence this module chose. **PostgreSQL is never exposed to a client** — the
bundle contains no driver, no connection string and no repository. See
[`security.md`](./security.md).

`npm test`, `npm run build`, `npm run smoke` and `npm run e2e` all pass with no
database present, and always must: with no `DATABASE_URL` the server runs the
demonstration store, which it says plainly on screen. **That is a choice, never
a fallback.** A deployment that has a `DATABASE_URL` and cannot reach it raises;
it does not quietly serve fabricated data.

## What exists

| | |
|---|---|
| **Schema** | `src/db/schema/` — split by domain area, barrelled through `index.ts` |
| **Migrations** | `src/db/migrations/` — five, applied in journal order |
| **Connection** | `src/db/client.ts` — lazy; importing it opens nothing |
| **Repositories** | `src/data/postgres/` — all eleven, behind the existing interfaces |
| **Composition root** | `src/data/backend.ts` — which persistence, decided once |
| **Reference data** | `src/db/reference-data.ts` — job types and machine types, from the domain |
| **Schema tests** | `src/db/schema.test.ts` — no database needed, part of `npm test` |
| **Integration tests** | `src/data/postgres/*.db.test.ts` and `src/server/api/http-api.db.test.ts` — `npm run db:test` |
| **Authentication store** | `src/server/auth/postgres-store.ts` — the only module that reads `users.password_hash` |

The migrations:

| File | What it does |
|---|---|
| `0000_initial_schema.sql` | Extensions, enums, 46 tables, indexes, CHECK constraints |
| `0001_job_numbering.sql` | The `eje_job_number_seq` sequence and `allocate_job_number()` |
| `0002_immutability.sql` | Triggers that refuse to rewrite a historical record |
| `0003_machine_photos.sql` | `machine_photos`, so a machine's own photographs persist |
| `0004_guard_fixes.sql` | Replaces a checklist guard whose local variable shadowed a column |
| `0005_api_idempotency.sql` | `api_idempotency`, so a retried request cannot perform a change twice |

`0000`, `0003` and `0005` are generated by `drizzle-kit`; `0001`, `0002` and
`0004` are hand-written and registered in `meta/_journal.json`. **Migration history is
append-only** — a correction is a new migration, never an edit to one that has
already run somewhere. **Do not regenerate `0000` without
re-adding the `CREATE EXTENSION` lines at the top** — `drizzle-kit generate`
does not know about them.

## Setting up a local database

```
createdb eje_dev
createdb eje_test
```

Then, with `DATABASE_URL` pointing at `eje_dev`:

```
npm run db:migrate
```

Both extensions (`citext`, `pgcrypto`) are created by the first migration and
need no superuser action beyond what a database owner normally has.

### Commands

| Command | What it does |
|---|---|
| `npm run db:generate` | Diffs the schema against the journal and writes a new migration. Needs no database. |
| `npm run db:migrate` | Applies pending migrations to `DATABASE_URL`. |
| `npm run db:check` | Verifies the migrations and the journal agree. Needs no database. |
| `npm run db:studio` | Opens Drizzle Studio against `DATABASE_URL`. |
| `npm run db:test` | Runs the integration tests. **Skips cleanly when `TEST_DATABASE_URL` is unset**, so it is safe to run anywhere. |

`db:test` rebuilds the public schema from the migrations on every run, so the
migrations themselves are exercised each time rather than assumed to work.

## Conventions

**Money is integer cents.** `bigint`, named `*_cents`, never `numeric` and never
a float. A schema test asserts every `*_cents` column is `bigint`. VAT is stored
as `vat_percent_basis_points` — hundredths of a percent, `1500` for 15% — for
the same reason.

**Timestamps are `timestamptz`.** The stored value is always the instant.
Presentation reads it in EJE's business zone through `src/lib/business-time.ts`,
so a signature date is the same date whether the document is rendered on a
tablet in Johannesburg or a server in UTC.

**Primary keys are UUIDs supplied by the application.** Not database-generated,
so a client can reference a record it has not sent yet — which the offline
mutation queue will need. `pgcrypto` is installed for anything inserted outside
the application.

**Mutable aggregates carry `version`.** Every update says
`where version = $expected`; zero rows changed raises `ConcurrencyError`. The
expected version is the one the *caller* read, not a fresh one, which is what
makes the second of two concurrent writers lose rather than silently win.

**Enums mirror the domain's closed unions.** `src/db/schema.test.ts` asserts
each one matches its union member for member, so adding a status without a
migration fails `npm test`.

**Job types and machine types are tables, not enums**, because the domain
docblocks already say they become administered rows.

## Immutability

Three shapes, enforced by triggers in `0002_immutability.sql` as well as by the
application:

| Shape | Tables | Rule |
|---|---|---|
| **Write-once** | `job_signatures`, `pricing_snapshots`, `pricing_snapshot_lines`, `final_documents` | No UPDATE, no DELETE, ever |
| **Append-only** | `audit_events`, `job_transfers`, `machine_approvals`, `chat_messages` | Insert and read only |
| **Frozen with one exception** | `signature_refusals`, `job_participants`, `delivery_attempts`, `checklist_instances`, `checklist_versions` | The recorded facts are fixed; one named set of fields may be filled in once |

A refusal is the clearest case. What the technician recorded — the reason, who
took it, when — cannot be changed. The office may set the resolution, once, from
null to a value. A second refusal is a **new row with `attempt = 2`**; attempt 1
is never overwritten.

The application layer already refuses these edits. The triggers are the second
line, against a mistaken migration or a well-meant support query.

## Job numbering

`EJE-####`, allocated by `allocate_job_number()`, which calls `nextval` on
`eje_job_number_seq`.

Not `max(job_number) + 1`, and not a counter in the settings row: both hand the
same number to two people raising a job in the same moment. `nextval` is atomic
and does not block. A rolled-back transaction leaves a **gap**, which is the
correct trade — a gap is a number nobody used, a duplicate is two job cards
claiming to be the same job.

The sequence starts at **1068** because the demonstration data runs EJE-1039 to
EJE-1067, so production numbering continues rather than colliding with
identifiers the tests and the demo depend on. `advance_job_number_sequence(n)`
moves it forward and refuses to move it backward.

## Which persistence, and who decides

`src/data/backend.ts`:

- `DATABASE_URL` present → PostgreSQL.
- `EJE_PERSISTENCE=demo` → the demonstration store, even where a database is
  configured. What a sales laptop wants.
- `EJE_PERSISTENCE=postgres` → demand PostgreSQL, so a missing `DATABASE_URL`
  fails loudly rather than quietly serving demonstration data to the business.

Nothing a browser can set takes part in this. `localStorage`, a query string and
a cookie are all things a visitor controls, and a data source a visitor can
choose is not a data source.

`withRepositories(work)` opens a transaction, builds every repository on it, and
runs the work. One executor for all of them is the point: an operation that
changes a job **and** opens a participation row **and** appends an audit event
either does all three or none. Each bundle is also one unit of work — the
repositories remember the row versions they read, so an optimistic update is
checked against what the caller actually reasoned about.

## Identifiers

Every primary key is `uuid` and the **application** supplies the value, which is
what lets an operation reference a record it has not written yet, inside one
transaction, without a round trip. `UuidGenerator` (`src/services/production/`)
is the production `IdGenerator`; the demonstration's `SequentialIdGenerator`
produces readable ids like `lab-m2k9-3` and the two are interchangeable at every
call site.

## Timestamps

`drizzle()` installs a transparent parser for every date and timestamp OID,
overwriting whatever the driver was configured with. Its intent is right — no
`Date` objects, because building one reintroduces exactly the local-timezone
ambiguity `src/lib/business-time.ts` exists to remove. What it leaves behind is
PostgreSQL's own text, `2026-09-20 12:00:00+00`, which is **not** ISO-8601.

The domain treats `IsoDateTime` as a string it sorts and compares — the activity
feed orders by `localeCompare`, the closed-job archive filters on `closedAt >=
from` — so `createDatabase` re-parses the two timestamp OIDs into ISO-8601 UTC
after drizzle has had the client. `date` stays `YYYY-MM-DD` and `time` stays
`HH:MM:SS`, which are already what the domain wants.

## Reference data

`syncReferenceData(db)` writes `job_types` and `machine_types` from the domain.
They are **not** demonstration data: `jobs.job_type_code`,
`checklists.job_type_code` and `machines.machine_type_code` are foreign keys to
them, so an empty database cannot store a single job until they exist.

It upserts and never deletes. A job type nobody raises any more is still named
by the jobs that were raised under it.

Machine types are keyed by a slug (`cnc_lathe`) and carry the label the domain
speaks in (`CNC Lathe`), so correcting a label's spelling does not orphan a
machine. The mapping lives in `reference-data.ts` and nowhere else.

## What is NOT stored, and why

- **`Customer.documents`.** Nothing in the application captures one — the field
  is written as `[]` at every site — so there is nothing to store and a table
  for it would be speculation. It gets a table when it becomes a feature, the
  way machine photos just did.
- **`SystemSettings.nextJobSequence`.** It has no column. A counter in a mutable
  row cannot allocate a job number safely; the sequence does that. The settings
  repository *reports* the number the allocator would hand out next and ignores
  the field on the way back in, so a settings write can never move the allocator
  in either direction.
- **Anything about a customer's refusal to sign, on the audit trail.** The
  reason lives on the refusal record and nowhere else, under
  `canSeeSignatureRefusal`. Passwords, session tokens and message bodies are
  likewise never recorded there.

## Still to come

- **No API.** No route handler exists. `withRepositories` is the capability the
  handlers will use, and until they exist the browser demonstration runs on the
  demonstration store.
- **No authentication.** `users.password_hash`, `sessions` and the security
  columns exist and nothing reads or writes one of them.
- **Outbound services are still simulated.** Microsoft Graph, WhatsApp Business
  and production file storage are each their own phase; `src/services/ports.ts`
  is the seam.
- **Audit archival is not automated.** `audit_events_archive` exists because the
  retention policy is agreed (Decision 7); nothing moves rows into it yet.
- **No import of existing business data.** Customers, machines, people, rates
  and the company details are business data and are captured by the business.
  Nothing here invents one.
